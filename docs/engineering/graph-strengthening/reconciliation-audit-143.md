# Reconciliation audit — the 143 high-confidence matches

**Status (2026-09-04): closed.** Machine analysis only. **No human has manually reviewed the 143
matches individually** — that is explicitly not what this document claims. See "What this is not"
below before citing this doc as evidence of correctness.

## What this is

`jeremy_wedding_candidate_reconciliation` (`reconcile-v1`, see D019) produced 143 candidate →
Ben-wedding matches at `match_confidence` 0.8 ("high-confidence"). Before deciding whether this
tier is trustworthy enough to build on, or whether reconciliation needs a redesign, this audit
analyzed all 143 using an improved both-sides review artifact
(`apps/web/scripts/graph/data/reconciliation_review/high_confidence_143.{csv,md}` — Jeremy-side
post URLs/vendors and Ben-side post URLs/vendors together, generated by
`exportHighConfidenceReview.ts`) and a scored risk-ranking pass
(`auditHighConfidence.ts` → `non_exact_ranked.json`). All read-only; nothing in this workstream
touched clustering, reconciliation, schema, or any production graph table.

## Method

1. **Deterministic tier**: for each of the 143, check whether any Jeremy candidate post URL
   exactly equals any Ben wedding post URL (`wedding_posts(wedding_id, post_id) → posts.url`, the
   authoritative source of a Ben wedding's Instagram posts). An exact shared URL means the Jeremy
   evidence and the Ben wedding are, in that instance, literally built from the same source post —
   the strongest identity signal available, stronger than any similarity heuristic. Per instruction,
   a date discrepancy does **not** override an exact URL match (posting-lag/extraction-timing
   noise, not identity noise).
2. **Non-exact tier**: the remainder were risk-scored (low vendor Jaccard, large date delta,
   sparse posts, tiny raw handle overlap, list-size mismatch, multi-candidate-to-one-wedding) and
   reviewed by diffing vendor **handles** (not just the role-labeled strings the Jaccard metric
   uses — role relabeling and handle typos across extractions understate true overlap) against
   both-sides evidence for each.
3. Each non-exact case was scored on same-wedding likelihood, vendor-overlap strength, and
   date-evidence strength, then given an overall GREEN/YELLOW/RED verdict, with a specific search
   for the highest-priority failure mode: a **false merge** (two distinct real-world weddings
   collapsed into one Ben wedding).

## Results

- **131 / 143 (91.6%)** have an exact shared Instagram post URL — treated as deterministic,
  auto-confirmed, no case-by-case review performed on these individually (verifying the join
  itself is correct, at scale, is not the same as verifying each match by eye).
- **12 / 143** non-exact, reviewed individually:

  | verdict | count |
  |---|---|
  | GREEN (same wedding) | 11 |
  | YELLOW (likely, flagged for a closer look) | 1 |
  | RED (different wedding) | 0 |

  The single YELLOW (candidate 2737 → wedding 1222) has strong vendor-handle overlap (11 of 14
  Jeremy handles present on the Ben side) but the largest date delta in the set (12 days, close to
  the reconciliation config's 14-day high-confidence window). Flagged for date evidence alone, not
  vendor disagreement.
- **Zero false-merge patterns found.** Only one Ben wedding (id 468) is targeted by more than one
  of the 143 candidates (candidates 2105 and 2116). Traced: candidate 2116 is itself an exact-URL
  deterministic match to wedding 468 (Jaccard 1.0, 0-day delta); candidate 2105 is vendor-evidence
  for the *same real wedding* that should have clustered into 2116 but didn't, because of a known
  order-dependent greedy-clustering bug (documented separately, see "Known issues" below).
  Reconciliation matched both correctly to the same real Ben wedding — the result is a redundant
  confirmation, not an incorrect merge.
- In every non-exact case reviewed, apparent weak overlap was attributable to measurement noise in
  the raw Jaccard score (role-label differences for the same handle, e.g. `content_creator` vs.
  `videographer`; handle typos/variants, e.g. `sazzcreations`/`saazcreations`,
  `djeetchicago`/`djjeetchicago`) rather than genuine vendor disagreement.

## What this is not

- **Not a human audit.** No person opened the 12 non-exact cases (or any of the 131 exact ones)
  and independently judged them against the source Instagram posts. All judgments above were made
  by the same automated/LLM-assisted analysis pass that also built the review artifact — it is not
  independent ground truth.
- **Not a claim that the 143 are error-free.** It is a claim that automated evidence — dominated
  by the 91.6% exact-URL tier, which needs no interpretation — is currently strong enough that a
  full manual audit is not the best use of time right now, and that no specific evidence of
  systematic error (especially false merging) was found in the portion that does require
  interpretation.
- **Not evidence about the ambiguous (268) or no-match (2,092) buckets.** This audit is scoped
  strictly to the 143 high-confidence tier.

## Decision

No reconciliation architecture redesign is justified by this audit. See D020.

## Known issues (not fixed here, tracked for future work)

**A. No evidence floor on weak reconciliation matches.** The reconciliation script assigns a
`matched_wedding_id` even at its lowest confidence bucket (0.1), with no floor — previously
measured to be the dominant cause of the "no-match" bucket's internal split (445 genuinely
venue-less vs. 1,647 weak-but-recorded matches) and the "magnet effect" where sparse Ben-venue
coverage inflates apparent candidate fragmentation. Target shape: strong evidence → match,
ambiguous evidence → reviewable/ambiguous, insufficient evidence → no match (null
`matched_wedding_id`, not a floor-value confidence). Not implemented as part of this audit.

**B. Clustering order dependence.** The wedding-468 case (candidates 2105/2116) demonstrates a
real, concrete under-merge: Jeremy's single-pass greedy clustering can fail to merge two posts of
the same real wedding into one candidate when an earlier post's date doesn't parse, changing
processing order. Confirmed not to cause false merges in reconciliation (see above), but it does
produce redundant/fragmented candidates. Remains a targeted clustering fix, not attempted here.
