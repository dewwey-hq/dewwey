# Venue concept page — golden-set template (v1 draft)

**Status:** Draft, derived from 4 hand-built concept pages (`apps/web/app/concept/`). Not locked — more archetypes are planned before treating this as final. Update this doc every time a new golden-set venue is built and it forces a template decision; that's the whole point of writing it down instead of leaving the reasoning buried in one venue's comments.

**Purpose:** these concept pages are not throwaway mocks — they're the reference standard for "organize a venue's messy real site into a page that makes a couple's life easier," which is a core product value, not a demo. Every new golden-set venue should be built *against this doc*, not against whichever existing page happens to feel closest. That's what keeps 8 venues from drifting the way the first 4 did before this doc existed.

## 1. Canonical section order — **locked**

Diamond Garden's order is the base pattern; Marchetti's placement of the wedding stack confirms where IG content slots in. Deviations in Field Museum/LondonHouse are drift from *when they were built*, not intentional archetype variation — confirmed by rereading all four; nothing about "being a museum" required Field Museum's different order.

```
Header (name, category, rating, address, website link, inquiry box)
About
Quick facts (pills)
[Wedding stack — Real Weddings / Vendor Stacks — conditional, see §4]
Photos
[Differentiator spotlight — conditional, see §4]
Space(s)
Food & Beverage
What's Included
Pricing            [only as its own section when the venue has multiple real pricing paths]
Add-ons & extras
Cost Estimate (calculator)
Policies
FAQs
[Featured Weddings — conditional, see §4]
[Vendors — conditional, see §4]
Location
Grounding footer (source pages + verified date)
```

Every page leads Header → About → Quick facts, no exceptions. Verified directly against Marchetti's actual code: the wedding stack sits **immediately after Quick facts, before Photos and Space** — not appended lower on the page. So the two real variants of the top of the page are:

- **Has real IG wedding content:** Header → About → Quick facts → Wedding stack → Photos → Space(s) → ...
- **No real IG wedding content:** Header → About → Quick facts → Photos → Space(s) → ... (Diamond Garden's placement — Photos moves up to fill the slot the wedding stack would otherwise occupy)

Codified now: **Photos sits right after Quick Facts whenever there's no wedding-stack content above it; otherwise it comes after the wedding stack and before Space.**

## 2. Standardized building blocks

These are locked — verified identical (or, where noted, converged on a best-practice format after a later venue improved on it) across the golden set so far, keep them that way. **A note on depth vs. structure, since it comes up every time a new venue is built:** the *formats* below are locked, but the *amount of real content* in a section is not, and shouldn't be forced to match. Diamond Garden's Food & Beverage section is far longer than Greenhouse Loft's because Diamond Garden genuinely has three real cuisine menus and a tiered bar list, and Greenhouse Loft genuinely doesn't; that's an honest reflection of what's real for each venue, not an inconsistency to fix. Never pad a thin section to look as full as a richer venue's, and never trim a rich section to look as short as a thin one — match the real content, keep the format.

- **About** — a couple of real sentences, not a generic paraphrase of the venue's category. **Check the venue's own top-of-page copy for a genuine distinction it leads with, and include it even if the same fact also gets its own row later (LondonHouse's fix, 2026-08-27: "with its unparalleled views of the city and experienced wedding planning services" — the venue's own site names its planning support as a headline distinction; the first-pass About only mentioned the views).** A fact appearing twice (once as the venue's own opening pitch, once as a structured What's Included/Policies row) isn't redundant — About is where a reader forms a first impression, and a paraphrase that quietly drops the venue's own headline claim reads thinner than the source it's summarizing.
- **Policies section** — same 13 rows, same order, every venue, verbatim: Catering, Bar, Venue rental charge type, Food & beverage minimum, Service charge, Parking, Day-of coordinator, Payment schedule, Cancellation / rescheduling, Event insurance, Security, Vendor access (setup/teardown), Noise curfew. A row with no real answer still appears, styled as `"Not stated (please confirm)"` in italic/grey — never omitted. This is the one section where "always show all 13, honestly greyed out" beats "hide what's unknown," specifically because couples comparing venues need the same checklist every time.
  - **Row format (locked, Greenhouse Loft's fix):** each row is a short, clear `value` shown as a small pill/badge (so the answer is scannable at a glance without reading a sentence), plus an *optional* smaller-font `detail` line below it only when the pill genuinely doesn't cover a real nuance. Don't give every row a detail line by default — that was the mistake the first pass made ("today this is too much... a user looks at catering and quickly understands the policy"). If the detail would just restate the pill in more words (e.g. a "Security: Included" row with a detail saying "Security personnel are provided"), drop the detail entirely.
    - **The pill must answer the actual yes/no or included/not-included question a couple is asking — not a related, softer one (LondonHouse's fix, 2026-08-27, caught on review: "some of our answers aren't clear enough").** Two concrete misses on the same page: Parking's pill said `"Valet only"`, which reads like parking is available/offered — the real, decision-relevant answer is that self-parking isn't included and valet isn't complimentary, so the pill was changed to `"Not included"` with the valet mechanism and rate moved to the detail line. Food & beverage minimum's pill said `"Amount varies"`, which leaves "does a minimum even apply?" unanswered — changed to a plain `"Yes"`, with the actual variability in the detail. Before finalizing any row, state the couple's real underlying question out loud ("is parking included?", "is there a minimum?") and check the pill actually answers it, not a nearby but easier question. This is the same discipline as the Add-ons naming fix below (say what's actually true, not a vaguer stand-in).
    - **Layout stays the divide-y row list (label left, pill + detail right) — confirmed, don't re-attempt a card grid.** A card-grid alternative (each policy its own bordered box in a 2/3-col grid, label-over-pill-over-detail stacked inside) was built and shipped on Greenhouse Loft (2026-08-26), then reverted the same session on direct feedback: "not as easy to find what you want if you're a viewer as how it was before." The row list's left-aligned label column is apparently what makes scanning-for-one-fact fast (eyes track down one column of labels); a grid breaks that because label position isn't fixed relative to the eye's scan path. Don't spend time re-trying this without new evidence it'd land differently.
  - **Real source documents (contracts, service agreements) that back up Policies facts get linked in this section's own `SectionHeading` actions slot** — not in Space, even if the document also happens to be about "the room": if its content is contract/policy terms (cancellation, insurance, rules, fees), it belongs where those facts already live. Space's action buttons are for "what does this look like" resources (tour, gallery, floor plans) only.
- **"Questions every couple asks" (the standardFaqs block)** — locked to exactly these 5 questions, same wording, same order, every venue (2026-08-25: previously each venue wrote its own 3–5 bespoke questions, which drifted venue to venue — standardized after noticing the same handful of questions kept recurring anyway): "Can we bring our own caterer, or does it have to be from an approved list?", "Can we bring our own alcohol?", "Is there a food & beverage minimum?", "Do we need to hire our own day-of coordinator?", "Is event insurance required?" These are deliberately the couple-voiced version of 5 of the 13 Policies rows (Catering, Bar, Food & beverage minimum, Day-of coordinator, Event insurance) — the ones couples ask first, before reading the full checklist. When a venue's real answer is unknown, use the same honest gap-filler as everywhere else: `"Not stated on their site. Confirm directly with the venue."` A venue-specific standout fact (e.g. Geraghty's wedding-vs-gala floor-plan capacity bug) belongs in the venue's own real FAQ list below this one, not as a 6th bespoke standard question.
  - **List visual format (locked, Greenhouse Loft's fix):** both FAQ lists (standard + the venue's real one) render as a bare list of full-width rows, each with its own bottom rule and a chevron on the right that rotates open on click — no outer bordered box, no divider lines between rows beyond the rule itself. This is deliberately different from Policies' bordered-box-with-pills look, now that Policies has its own distinct pill treatment (see above) — the two sections need to read as visually distinct question-and-answer vs. checklist formats, not the same boxed-row component reused twice.
- **Capacity tiles** — always 3 tiles in a row, driven by a per-venue `capacityLabels` object (labels are real venue vocabulary, not forced into one universal set — Marchetti says "Seated Dining / Seated w/ Dance / Standing Reception," Diamond Garden says "Seated / Seated w/ Dance Floor / Cocktail"). **Always render all 3 tiles even if a venue only has a real number for one** — unstated tiles get the grey `—` treatment (Diamond Garden's explicit fix, keep it: "i still want all three tiles" applies to every future venue, don't collapse to fewer tiles just because data is thin).
- **What's Included** — venue-wide facts true regardless of package/tier/path, pulled into their own section (not buried in a package card). Only include when the venue genuinely bundles baseline stuff across every package — if there's only one package and nothing is "shared," skip the section rather than forcing it. **"Genuinely nothing shared" is a high bar, not a low one — 2-3 real cross-package facts (a climate-control fact, a linens/getting-ready-room inclusion) is enough to justify the section, even when it feels thin next to a richer venue's version (2026-08-26, Marchetti's fix: "i think we need a what's included section even if it's more bare").** A deliberately bare, honest section beats omitting real facts just because there aren't many of them — the "empty beats wrong" principle (§4) is about not inventing content, not about a minimum item count.
  - **Row format (locked):** every item is a short bold **label** plus a one-line **detail** ("Tables: 25 farm tables (8'×30") and 10 cocktail tables (28")"), not a bare sentence — a plain sentence like "10 28'' custom cocktail tables" doesn't make clear at a glance what the fact is about; leading with the category name fixes that. Each item gets its own icon (map real item → icon, fallback to a generic sparkle icon) rather than one repeated checkmark.
    - **When one item IS the venue's real differentiator, let the label say so instead of a generic category noun, and lead the detail with what it means before the physical inventory (2026-08-26, Greenhouse Loft's fix — took three feedback passes to land on this for one line, worth doing right the first time on the next venue).** Greenhouse Loft only ever books one wedding a day; the first draft called this item "Space" with the fact buried mid-sentence ("The entire venue, all yours for the day: the loft, outdoor Skygarden, and art gallery"). Landed on label **"Exclusively yours"** (the selling point itself, not "Space"), detail **"When you book, you're the only wedding that day. The loft, outdoor Skygarden, and art gallery are exclusively yours."** — human-terms meaning first, concrete inventory second. Check every venue's real "how many events per day" answer for this: it's a genuinely differentiating fact for a single-event-at-a-time venue (vs. a shared-building/multi-event venue), easy to flatten into a plain inventory line instead of leading with what it means for the couple. Marchetti's real answer to this question hasn't been re-checked since — worth doing on the v4 pass.
  - **Grouping (locked, Greenhouse Loft's fix):** once a venue has more than ~6-8 real items, group them into labeled subcategories with small uppercase micro-headers (same visual language as Food & Beverage's "Food"/"Bar" sub-headers) instead of one flat list — a flat list of 15 items reads as a blur. Greenhouse Loft's categories are the reference shape: **Space** (the room/rental itself, parking, coat check, bridal suite, and any fixed/built-in structure — see the Space-vs-Furniture test below), **Furniture** (tables, chairs — movable items guests sit at/use, arranged per event), **Entertainment** (DJ, sound/AV, photobooth, videography), **Services** (coordinator, security — real people/staff), **Ambiance** (candle treatment, décor, and similar atmosphere items). These are examples of the *kind* of split to make, not a fixed taxonomy every venue must reuse verbatim — name categories after what's actually true for that venue, but keep the same discipline: don't mix people/services in with décor just because both feel like "extras" (that was the bug this fixed — the old "Staff & extras" catch-all mixed a coordinator with candle treatment). A venue with only 4-5 items can stay a flat list; grouping is a readability fix for volume, not a mandatory shape.
    - **Category names must be concrete, not a vague catch-all like "Perks" or "Extras" (LondonHouse's fix, 2026-08-27: "perks is nondescript").** LondonHouse's Lodging-related items (complimentary suite, parent upgrades, room block) were grouped under "Perks," which describes how the couple feels about the items, not what they actually are. Renamed to **"Lodging"** — the same discipline as the Space-vs-Furniture test above: name the bucket after the concrete concept the items share (lodging, furniture, entertainment), not a vibe or a value judgment. If you can't name a group after what its items concretely are, that's a sign the items don't actually belong together yet.
    - **Space-vs-Furniture test (2026-08-26, Greenhouse Loft's fix):** a built-in/permanent fixture of the room (Greenhouse Loft's "25' *permanent* bar") goes under **Space**, next to Bridal suite/Coat check, not Furniture — even though it's superficially bar-shaped like a table. The test is "is this bolted down / part of the room" vs. "is this a movable item that gets arranged per event and that guests directly sit at/use." Greenhouse Loft's first pass grouped its bar under Furniture next to Tables/Chairs on the "it's a physical thing, not a service" logic, which is true but too coarse — moved once someone actually looked at it next to the other Space items and it fit better there.
  - **Scope discipline:** only list things the venue actually *provides as part of the booking*. A policy about what's *allowed* (e.g. "open catering list," "BYOB") is not an inclusion — it belongs in Policies/Food & Beverage instead. Greenhouse Loft's first pass wrongly listed "Catering: open list" here; an open catering list is a permission, not something the venue supplies.
  - **Before inventing a label or icon for a new item, check the rest of the golden set for the same underlying concept and reuse it verbatim (2026-08-26, Marchetti's fix — "ensure the icons and like text is similar venue to venue/standardized").** Two venues both having climate control, or both having a private getting-ready space, is common — those should render identically everywhere, not get a bespoke label/icon per venue. Concretely: Marchetti's first pass invented its own icon for "Heating & A/C" (`Thermometer`) instead of reusing Greenhouse Loft's existing `AirVent` for the exact same fact, and labeled a getting-ready room "Floor-length linens"/"Private Wedding Salon" (the venue's own branded name) instead of Greenhouse Loft's generic "Linens"/"Bridal suite". Fix: the **label** is the generic, cross-venue category noun (matches whatever the golden set already uses for that concept); the venue's own specific/branded name or measurement goes in the **detail** line instead (e.g. label `"Bridal suite"`, detail `"Both The Pavilion and La Pergola have their own Private Wedding Salon..."`). This is the same instinct as the Policies section's standardized labels (§2, Service charge) applied to What's Included.
  - **Check the venue's real FAQ specifically for HVAC/climate and ADA/accessibility, even after the main pass feels done (2026-08-26, Greenhouse Loft's fix).** Both are common real FAQ questions ("How's the HVAC?", "Are you wheelchair accessible?") that answer real, decision-relevant facts, but don't naturally surface anywhere else on the page the way DJ/parking/tables do — so they're easy to leave sitting unsurfaced in the raw FAQ list below and never make it into a structured field. **HVAC/climate control** and **ADA/accessibility** — if genuinely stated, both go as their own What's Included items under **Space** (fixed facts about the building, same bucket as Parking/Coat check/Bar space), not folded into another row or into the Space section's prose `description` — tried the HVAC fact as a `description` sentence first, moved it to What's Included the same session on direct feedback ("it goes better there"). Neither is a quick-facts pill; that slot is reserved for a truly distinctive 5th pill per §3, and climate control/accessibility are closer to baseline-expected than differentiating for most venues (Marchetti's real `climate` pill is the exception, because it's a converted industrial loft where the answer was genuinely in doubt).
    - **A direct user question about a fact is a trigger to re-verify it fresh, even when an existing code comment already says "checked, not found" (LondonHouse's re-check, 2026-08-27).** LondonHouse's `data.ts` already had a comment saying HVAC/A-C was checked on `/amenities` and absent; asked again directly on review, it was worth re-fetching anyway rather than trusting the old note — sources can change, and a prior pass's comment isn't proof against a stale or incomplete check. Re-confirmed absent on both `/amenities` and `/weddings` this time, including the FAQ accordion, which turned out to live on `/weddings` itself rather than a separate FAQ URL — worth checking where a venue's "FAQ" content actually lives before assuming it's a page of its own.
- **Food & Beverage packages with a named sub-collection per tier** (e.g. each package bundling its own bar tier — Marchetti's Villa/Tenuta/Riserva Bar Collections under Argento/Oro/Platino) — **add a couple of real example items per tier so the escalation is visible on the page, not just implied by the sub-collection's name changing (2026-08-26, Marchetti's fix — "maybe we want to include the bar distinction... from argento thru platino").** A name alone ("Tenuta Bar") doesn't tell a couple what's actually different; 2-3 real example items per tier (from the venue's own published list, trimmed down, not the full 10-20 item menu) does. **Any shared explanatory note about how the tiers relate reads as a footnote below the package cards, not a lead-in above them (2026-08-26: "feels like a note underneath not on top/above the bar packages")** — a reader should reach the actual prices first; the explanation is supplementary context, not a barrier to get through.
- **Add-ons & extras** — curated, never an exhaustive PDF transcription; link the source PDF for the full list. No subtitle that reads like a note to a colleague ("beyond the base rental, genuinely short since...") — if the section needs an explanatory aside, that belongs in a code comment, not on the page the couple sees. Two valid shapes, pick based on what the venue's real add-ons actually look like:
  - **Category + table** (Diamond Garden's shape) — use when a category genuinely has multiple related line items sharing the same two columns (e.g. 3 tiers of a food package, 6 bar tiers).
  - **Per-item card** (Field Museum's shape, Greenhouse Loft's fix) — use when each add-on is one discrete real thing, not a menu of tiers: icon, name, price, one-line description, with the icon beside the text (not stacked above it). This is the more common case — most venues have a handful of standalone extras (parking upgrade, rehearsal time, a cleaning fee), not menus of tiers, so default to this shape unless a category genuinely needs the table.
  - **The decision rule between the two shapes is about how many axes the pricing varies along, not preference (2026-08-26, Marchetti's fix — asked for explicitly: "preference is for extras and add-ons to have it more like greenhouse... but obviously this overflows... i think that logic is an example of something good to document").** A card can cleanly show *one* axis of variation as a short internal list (Marchetti's Food & Beverage experience cards vary by tier only — Signature Moments vs. Signature Experiences — and stay a card fine). It cannot cleanly show *two* independent axes at once — e.g. a named style variant (White vs. Black & white dance floor) **and** a separate per-space/per-venue price (La Pergola vs. The Pavilion) for each variant. Forced into a card, that becomes a small table-in-disguise (variant name, then a price line per venue, repeated per variant) with none of a real table's column alignment — worse for scanning, not better. **Marchetti's Space & rentals actually tried the card conversion (2026-08-26) and reverted it the same day** ("the table was best way of showing that") — same class of outcome as the Policies card-grid revert above; don't re-attempt a card for a genuinely 2-axis dataset without new evidence it'd land differently. Rule of thumb: count the independent things a price varies by (variant, space/venue, day-of-week, season, guest count...). One → card. Two or more → table, with one axis as rows and the other as columns.
  - **Scope discipline (Greenhouse Loft's fix):** only real, *purchasable* extras belong here (corkage fee, ceremony fee, extra parking, rehearsal time). Required third-party costs (event insurance) and payment-method surcharges (a credit-card fee) are not add-ons — they're already Policies facts or Cost Estimate calculator inputs, and listing them again here is both redundant and mislabeled. A contingent cost with no fixed public number (e.g. a cleaning fee that's "the greater of a flat fee or actual cost") is still a real add-on — show it honestly as "not stated" rather than omitting it or inventing a number. **A cost with genuinely no dollar figure at all (e.g. "fee varies by staffing," no number published anywhere) still gets listed here for the couple to see, but must be excluded from the Cost Estimate calculator's selectable extras** — see that subsection below; showing it in the reference list while silently pricing it at $0 if a user "selects" it in the calculator is worse than either showing it consistently or not at all.
  - **A conditional add-on (its price only applies if a real yes/no decision goes one way — e.g. a ceremony fee that's only charged if the ceremony is held on-site) should name that condition as the item's own option/variant label, not leave it as a bare, unlabeled "Add" (2026-08-26, Marchetti's fix — "instead of ceremony fee add it should be like ceremony on-site yes, no").** Concretely: give the variant a real name (`"On-site ceremony"`) instead of `name: null` — this shows up in both the static table's Option column and the Cost Estimate chip's label, so the condition is legible in both places without needing to read the item's separate note text. Reserve this for genuinely conditional fees; a plain optional extra with no gating condition (a stage, chiavari chairs) doesn't need it — relabeling those wouldn't add clarity, since "do you want to add this" is already the whole story.
  - **Naming:** plain, couple-facing names ("Additional Parking," not "Parking upgrade") — this is a page for a couple, not internal shorthand.
  - **A real add-on with no public price should say `"No published rate"`, not the bare placeholder `"Not published"` (LondonHouse's fix, 2026-08-27: "no published isn't descriptive enough").** "Not published" reads like a sourcing gap on our side; "No published rate" reads like the actual fact — this add-on exists, and LondonHouse itself hasn't put a number on it. Same "state what's actually true" discipline as the Policies pill-wording fix above, applied to Add-ons.
  - **Don't append a tax-rate suffix to one item's static price (e.g. `"$750 (+15.75% tax)"`) when every add-on is equally subject to sales tax (LondonHouse's fix, 2026-08-27: "delete +15.75% tax... include that in our cost estimate").** Calling out the rate on a single card reads like that item is uniquely taxed, when the real fact is every add-on carries tax the same way food & beverage does — singling one out is confusing, not more transparent. Keep the static card's price clean and do the actual tax math in the Cost Estimate calculator instead (see the calculator's Taxes group below), which is where a couple actually needs the number to be real.
- **Cost Estimate calculator vs. Pricing section — two different things, keep them separate.** Pricing = "what we know" (real published numbers, presented as fact). Calculator = an interactive guide, explicitly not framed as a quote. Don't merge them into one section; the distinction matters for not implying a binding number.
  - **Fixed inputs (locked shape, LondonHouse's pattern):** a 3-column grid with dividers (`sm:grid-cols-3 sm:divide-x`), each column a small uppercase label over either a guest-count stepper or a `PillGroup`. Guests is always one of the three; the other two are the venue's real configurable choices (package/day/season/ceremony-yes-no/etc.). A binary yes/no fact that affects the estimate (e.g. "planning a live band?") gets the same labeled-PillGroup treatment as everything else, not a bare unlabeled checkbox.
  - **Guest stepper gets a small range reminder underneath it (locked, LondonHouse's pattern, generalized 2026-08-26):** `<p className="mt-1.5 text-[11px] text-gray-400">` showing the venue's real range — either `{min}–{max} guests` (or "seated," matched to whatever the venue's own max actually measures — Greenhouse Loft's calculator max is a cocktail-standing number, not seated, so it says "guests," not "seated") or, when there's only one real ceiling worth stating, `Up to {max} seated` (Marchetti's shape). Don't make a couple scroll up to Quick facts or Capacity tiles to remember the venue's real range while they're mid-slider.
  - **`PillGroup` option order: lead with the affirmative/default/more-commonly-chosen option, not alphabetical or negative-first (2026-08-26, Greenhouse Loft's fix).** A yes/no toggle reads `Yes` then `No` (not `No, Yes`) — say the answer the way a person would, affirmative first. A tiered choice like Season leads with the option couples pick more often (`Peak season` before `Off-season`) rather than the order the venue's own rate table happens to print them in. This is a small thing but was flagged directly as "the order is weird" — apply it to every future venue's calculator, not just this one.
  - **Optional add-ons (locked shape, Diamond Garden's pattern): collapsed by default behind an "Add extras" button with a chevron that rotates open**, showing a `(N selected)` count when something's chosen — not always-visible chips taking up permanent space. Real optional purchasable extras go here (parking upgrade, rehearsal hours). **A payment-method choice (cash/check vs. credit card) is a fixed input, not an "extra"** — it doesn't add a discrete thing to the event, it changes how the existing total is billed; give it its own labeled slot next to Day/Season/Band, not a chip in the extras panel.
    - **A real, per-unit-priced add-on (e.g. a $/bottle corkage fee) gets a quantity stepper inside the panel, not a plain on/off chip (LondonHouse's pattern, 2026-08-27).** A flat extra ("Additional Parking, $150") is a binary pick; a per-unit one needs a count to price correctly — reuse the same Minus/Plus stepper visual as the guest-count control, scoped small, right in the extras panel.
  - **When add-on options are generated generically from the Add-ons & extras data (e.g. looping over every rentals category to build chips), explicitly filter out any item with no real dollar figure — never let it silently price at $0 (2026-08-26, Marchetti's fix).** A generic loop is the right approach (new add-on categories should "just work" without bespoke code per venue — Marchetti's real ceremony fee did, automatically, once added to the underlying data), but it needs a guard: an item like "fee varies by staffing, no price published" (Marchetti's Coat check) would otherwise become a selectable chip that adds literal $0 to the total if picked, misrepresenting a real but unquantified cost as free. Filter these out of the calculator's selectable set (they still belong in the static Add-ons & extras list for reference — see that section's scope-discipline bullet above); don't invent a placeholder number to make the filter unnecessary.
  - **Taxes & fees get their own line in the breakdown table, always** — even when the true answer is "included in the rental rate, nothing added." State it (grey/italic, e.g. `Taxes & fees: Included in rental rate`) rather than silently omitting the line, the same "show it, honestly" instinct as Policies' 13-row rule.
    - **Give the tax line its own group header row, styled identically to Venue/Food & Beverage/Space & rentals's own headers, with a real top-border break above it — don't let it just trail as the last line item under whatever group happens to render immediately above it (2026-08-26, Marchetti's fix: "looks grouped").** When a group above the tax line is conditionally rendered (e.g. "Space & rentals" only appears once something's actually selected), a tax line with no header/divider of its own visually reads as belonging to that group specifically, rather than as its own thing applying across the whole estimate. Give it a `"Taxes"` header exactly like the other groups get.
    - **Default assumption, absent a venue stating otherwise: sales tax applies to food & beverage and to rented goods/add-ons, not to a flat venue/room rental fee itself (2026-08-26, Marchetti's fix — asked directly: "should the sales tax be on everything?").** A pure space-rental charge is typically not itself subject to general sales tax the way prepared food, beverage, and physical rentals are, even when a venue's own site is vague ("applicable sales tax will be added to all taxable charges," without naming which charges those are). Compute the tax base as food & beverage + rentals/add-ons only, and say so in the line label (e.g. `"Sales tax (11.75%, on food & beverage and rentals)"`) so it's clear at a glance rather than implying the whole total is taxed.
    - **Group order (locked, LondonHouse's fix, 2026-08-27: "the category order is confusing with ceremony underneath taxes"): every real charge group (Venue, Food & Beverage, any conditional fee like Ceremony, Add-ons) comes first, in the order a couple would incur them; one consolidated Taxes group comes last, immediately before the total — never interleaved between charge groups.** LondonHouse's first pass put a general "Taxes" group right after Food & Beverage, then a separate Ceremony fee-plus-its-own-tax group *after* that — which reads as two disconnected tax groups rather than one. If a venue has more than one real tax rate (LondonHouse's general sales tax vs. its higher ceremony-fee-specific rate), every rate's line still lives inside the single Taxes group, each on its own labeled row (e.g. `"Ceremony fee tax (15.75%)"` next to `"Sales tax (11.75%, on food & beverage)"`) — don't split them into per-charge tax groups just because the rates differ.
  - **A real, required-but-uncounted cost (e.g. mandatory third-party event insurance) is shown as its own "Not included above" table row with a real estimate**, not summed into the total (it isn't paid to the venue) and not buried in a footnote sentence below the table — put it where the couple will actually see it.
  - **Total row label: `Estimated total (includes tax)`** (LondonHouse's exact wording) — use it verbatim even when, as above, "includes tax" really means "tax is already baked into the rate with nothing added," so every venue's calculator ends the same way.
- **Grounding footer** — every page ends with "Sourced from N pages on [domain] · verified [date]" plus the literal source URLs. Non-negotiable — this is the trust mechanism, not decoration.
- **Section-heading action buttons** — resource links (PDFs, menus) live in the `SectionHeading`'s own `actions` slot at the top of the relevant section, not scattered as inline links mid-section (Diamond Garden's fix after "looks a little weird having them by food and then below them are the pills").
  - **Button size (locked, 2026-08-26): `px-3 py-1.5 text-xs font-medium` with a 13px icon** — `inline-flex shrink-0 items-center gap-1.5 rounded-lg border border-rose-300 bg-white px-3 py-1.5 text-xs font-medium text-rose-500 hover:bg-rose-50`, icon `size={13}`. This is what Greenhouse Loft's and Marchetti v4's resource buttons (catering guidelines, service agreement, brochure) already use; written down here because `londonhouse-chicago-v2` initially copied v1's older, larger button (`px-3.5 py-2 text-sm`, 14px icon) by not checking newer venues first, and it visibly didn't match once compared side by side. Applies to every button in a `SectionHeading`'s `actions` slot, not just PDF links — floor-plan/video/tour buttons included, unless a venue's specific pattern (e.g. `PageLightboxButton`, `FloorPlansButton`) already matches this sizing on its own.
- **Single-space vs. multi-space rendering** — 1 real space → one centered card (~65% width, Diamond Garden). 2+ real spaces → a 2-up grid of full-width cards (Marchetti, Field Museum), plus a line above the grid for any real "book both together" combined pricing if it exists.
  - **When a multi-space venue's package price is stated as one flat rate "regardless of room," verify that directly against a primary source rather than assuming a hotel/single-operator venue always prices this way (LondonHouse's fix, 2026-08-27: "is it really same cost for both spaces?").** LondonHouse's per-guest package price is genuinely space-agnostic — confirmed by the venue's own `/weddings` page stating one price range with no room-specific figure anywhere — but that's a fact to check per venue, not a default to assume. If the full sourcing document needed to check this is too large for the tooling at hand (LondonHouse's 14MB wedding-menu PDF exceeded `WebFetch`'s size limit), rely on whatever already-fetched, smaller source states the same fact directly, and say so in the code comment rather than silently treating the assumption as verified.
  - **A genuinely different physical structure between spaces (tented vs. glass-enclosed roof, indoor vs. semi-outdoor) gets its own short label right next to that space's sq ft in the card header — not left buried inside the paragraph `description`, and not left as a hover-only quick-facts tooltip (2026-08-26, Marchetti's fix — "i think we should more prominently say it's tented").** Marchetti's Pavilion is a literal tent, La Pergola is a permanent glass-enclosed room with a retractable roof — a real, decision-relevant difference (weather/ambience expectations differ) that was previously only mentioned mid-paragraph and in a pill's `title` attribute (invisible on mobile, easy to miss even on desktop). Fix: a `structureLabel` per space (`"Tented ballroom"` / `"Glass-enclosed, retractable roof"`), rendered as `{sqFt} sq ft · {structureLabel}` right under the space name — same prominence tier as sq ft itself, since it's the same kind of "what am I actually renting" fact.
- **Real resources & media (tours, videos, floor plans, menus/PDFs)** — capture every real resource a venue publishes, using the right presentation for each:
  - **Resource links default to an in-page lightbox, not a new tab (locked, 2026-08-27: "maybe we should just show all of them lightbox style... that way users stay on page instead of leaving/easier").** Every PDF, hosted page, or video a venue publishes — brochure, menu, capacity chart, floor plan, video, contract — should keep the reader on the concept page rather than sending them out to a new tab, by default. Use the shared `apps/web/app/concept/_shared/ResourceLightboxButton.tsx` component (generalized from Greenhouse Loft's `PageLightboxButton`/Field Museum's `VideoTourButton`, first written for `londonhouse-chicago-v2`): it renders the locked action-button size above, and opens a fullscreen lightbox with a close button, a title, and an **"Open in new tab" link that must always stay present** — this is a convenience default, never a way to trap a reader on the page. PDFs need no special handling beyond pointing the iframe at the file URL; the browser's own inline PDF viewer renders inside it.
    - **Embeddability is a per-URL fact you must check before wiring a resource to the lightbox, not something the component can detect at render time.** Run `curl -I <url>` (or `curl -sIL <url>` if the host redirects) and look for an `x-frame-options` header or a restrictive CSP `frame-ancestors` — either means the response can't be framed and the iframe will fail silently or render blank. This generalizes the existing "never guess an embed URL" rule below (Field Museum's Vimeo bot-wall, Diamond Garden's Wix Access-Denied) to PDFs and hosted pages: `galleria-marchetti-v4`'s brochure is the first confirmed case (`framerusercontent.com` serves it with `x-frame-options: DENY`, checked 2026-08-27) — it stays a plain new-tab link, with a code comment explaining why, exactly like the Vimeo/Wix cases below.
    - **A video resource (YouTube, Vimeo) embeds via the platform's standard player URL** (`youtube.com/embed/{id}`, `player.vimeo.com/video/{id}`) inside the lightbox's `frame="video"` mode (a black `aspect-video` box, vs. the default white page/PDF card) — same idea as Field Museum's pre-existing Vimeo embed, now folded into the shared component instead of living in its own bespoke button.
  - **Floor plans** — per-space lightbox button next to that space's name/sq ft (Marchetti's `FloorPlanButton`) when a venue has distinct floor-plan *images* per room; the shared `ResourceLightboxButton` above when floor plans are PDFs instead (LondonHouse's capacity chart, Greenhouse Loft's two floor-plan PDFs — the latter picked from a small dropdown menu, since there's more than one document, but each opens in the same lightbox once selected rather than a new tab).
  - **Virtual tour / wedding videos** — a button per space (or per Space section when there's only one space) linking to the real tour/video. **Embed directly only when a real, confirmed-working embeddable URL exists (see the `curl -I` check above); otherwise link out to the venue's own page — never guess a predictable embed URL.** This already happened twice for real reasons worth repeating as a standing rule: Field Museum's Vimeo had a bot-check wall, and Diamond Garden's Wix tour/video pages hydrate client-side from a JSON endpoint that returned Access Denied on the predictable URL. Both link out instead of faking an embed.
  - **Menu / bar-package / add-ons PDFs** — surfaced as buttons in the relevant section's `SectionHeading` `actions` slot (Food & Beverage, Add-ons & extras), never buried inline, and default to the lightbox above rather than a new tab. When a PDF's real content is worth showing (not just linking), transcribe it into real structured fields (Diamond Garden's `foodMenus`/`barPackages` tables) rather than leaving it as a link-only PDF — but only when the source is genuinely readable; a link-only PDF is fine when it isn't.
  - Same non-negotiable as every other fact: only link a resource whose real URL was actually found. No inferred/guessed URLs, ever — say so in the file header comment when a resource couldn't be confirmed, same as any other sourcing gap.
  - **Placement is by topic, not by "which section is about the venue"** — a resource goes in the `actions` slot of whichever section already covers the same ground: floor plans/tours/galleries → Space (what does it look like); menus/bar lists/catering guidelines → Food & Beverage; a full contract/service agreement/insurance-requirements document → Policies (it's contract terms, not a "picture the room" resource, even though it's technically about the venue's space). When unsure, ask what question the document answers, then find the section that already answers that kind of question.
    - **Exception: when one document is broad enough that no single later section is a clean topical match, link it from About instead (2026-08-26, Marchetti's fix).** A consolidated real wedding brochure often covers Food & Beverage, Add-ons, and Policies all at once — forcing it into just one of those sections buries it for a reader who scrolls straight to a different one. About is the first section on the page, so a reader can grab the whole document before diving into any one topic.
  - **Actively look for a consolidated "wedding brochure" PDF, not just per-topic PDFs (menus, contracts) — it's often the single richest source on the page (2026-08-26, Marchetti's fix: "looks like there's a wedding brochure here... consider it").** A brochure built for handing to couples tends to consolidate facts that are otherwise scattered across many separate pages of the live site (pricing, fees, policies, FAQ-style info all in one place), and is sometimes hosted off the venue's own domain entirely (Marchetti's was a static asset on `framerusercontent.com`, from the site being built in Framer) — so don't assume "not on the venue's domain" means "not real." Read it in full before concluding a venue's page is done; it's a plausible source of genuinely new facts (Marchetti's brochure alone surfaced a ceremony fee, a coat-check fee, a corrected capacity number, and a real conflict between two of the venue's own documents on payment timing) even after every page in the sitemap has already been checked.
- **Wedding stack format — locked to Marchetti v3's implementation.** When real IG wedding content exists, use its exact components: `RealWeddingDeck` (card-stack deck of real weddings) inside the tinted `#fdf8f5` band (no divider lines — the tint band itself is the section boundary), with `VendorCategoryList` for the Vendors section pulling from the same real per-wedding vendor credits. This is now the reference implementation to reuse, not just one example among several — the next IG-backed venue should reuse these components directly, not rebuild the pattern. **Caveat found building `geraghty` (2026-08-24, the second real implementation of this pattern):** Marchetti's `VendorStackDeck`/`RealWeddingDeck` vendor-category icons point at `/icons/*-svgrepo-com.svg` files that no longer exist in `apps/web/public/icons` — deleted by the 2026-08-23 "Slot storefront" commit's sweep to one Phosphor icon family, which never touched `/concept` (not part of the main app's build/lint path, so nothing caught it). Marchetti's and Field Museum's vendor-category icons are currently broken images in production. `geraghty`'s copy of these components uses `lucide-react` instead (already a dependency, no missing-asset risk) — reuse *that* icon approach for the next IG-backed venue, not Marchetti's original file, until someone fixes or removes the dead asset references on the first two pages.

## 3. Pill & icon vocabulary — **locked**

**Quick-facts icons (top-of-page pills):** one canonical set — `guests`, `setting` (indoor/outdoor/both — Diamond Garden's `setting` key wins over the older `indoorOutdoor` name; rename `indoorOutdoor` to `setting` wherever it still appears), `catering`, `bar`. A 5th archetype-specific pill is allowed on top of these four **only** when it's a genuinely distinctive, decision-relevant fact for that venue (Marchetti's `climate` — a real "Heating & A/C" differentiator for an event-loft archetype). Don't invent a 5th pill to fill space; omit it when the base 4 already cover what's true. **Being real and true isn't sufficient on its own for the 5th-pill slot — it has to be genuinely decision-blocking, and that call can go either way even for the same venue on review:** LondonHouse's on-site guest rooms/room block was tried as a `hotel` 5th pill, then cut on a later pass (2026-08-27: "i dont think room block is a pill we should include") — a real, useful amenity, but not decision-relevant enough to earn the scarce slot the way Marchetti's climate uncertainty is. The room-block/suite-upgrade facts still belong on the page, just in What's Included's Lodging group, not the top-of-page pill row.
  - **Label format for `catering`/`bar` (locked, Greenhouse Loft's convention, generalized 2026-08-27): `"Category: Answer"`** — `"Catering: BYO (open list)"`, `"Bar: BYOB"`, `"Catering: In-house"`. LondonHouse's first pass used un-colon'd phrasing (`"Catering in-house"`); standardized to the colon form since it reads as a labeled fact rather than a floating adjective. `guests`/`setting` don't need the colon — a bare `"Up to 190 guests"` or `"Indoor"` already reads fine, since the icon alone establishes the category there.

**Food & Beverage pills — BYO / À la carte / All-Inclusive, mandatory on every venue's Food & Beverage section, and additive, not exclusive.** Every golden-set venue's page must render at least one of these three pills for Food and at least one for Bar somewhere in the section — this is not an optional flourish, though the *layout* that satisfies it varies (see below). A venue can genuinely support more than one, and when it does, show every pill that's true simultaneously — Diamond Garden supporting all three at once is the right shape to expect on a genuinely open venue, not an edge case to normalize away into one pill.
  - `BYO (Bring Your Own)` — couple can bring their own caterer/bar service, no venue restriction to a list.
  - `À la carte` — venue offers individually-selectable food/bar items or packages (not one bundled all-in price).
  - `All-Inclusive` — one bundled per-guest (or per-package) price that already covers food/bar/service together.
  - **Research rule, not just a display rule:** when building a new venue, actively check for all three on the venue's own site (packages page, FAQ, "can we bring outside catering" question) rather than defaulting to whichever option the venue's marketing headlines. A venue's homepage usually pushes its most profitable package, which under-reports how flexible it actually is — Diamond Garden's third pill (BYO) only surfaced because the FAQ was read directly, not inferred from the packages page alone. First pass should lean toward finding the broadest true set, then only show what's actually confirmed — never show a pill that isn't backed by a real quote.
  - Exclusive-in-house venues (Marchetti: "No outside caterer option," verified quote) correctly show **only** `All-Inclusive` — a single pill here is a real finding from having checked, not a sign the research was incomplete.
  - **Rendering is its own checklist item, separate from having the fact** (2026-08-26, caught building `londonhouse-chicago-v2`): `galleria-marchetti-v4`'s own Food & Beverage section rendered no pill at all, on either Food or Bar, even though the underlying fact was already sitting right there in `quickFacts`' catering/bar notes ("No outside caterer option," "Bar in-house") — a rendering gap, not a research gap, and it slipped through that page's own template-reapplication pass. When building or reviewing any venue's Food & Beverage section, treat "does a pill actually render here" as its own explicit check, not something that follows automatically from having sourced the fact.
  - **Layout: two shapes, picked by whether Food and Bar have anything different to say (2026-08-26, Marchetti's fix).** A first pass at this fix split every venue into labeled "Food" and "Bar" subheaders, each with its own pill and a prose sentence — Greenhouse Loft's real shape. Tried the same shape on Marchetti and it read as redundant (feedback: "no need to do food, bar and the new lines... redundant. concise clear simple intuitive"), because Food and Bar shared the identical `All-Inclusive` pill there and the prose was just restating what the package cards immediately below (and the quickFacts notes above) already say. The rule: **use the labeled Food/Bar subsections with their own prose only when the two sides genuinely have something different to say** — different pill values, or a real fact worth stating per side that isn't already visible right below (Greenhouse Loft: a linked composting-guidelines PDF for catering, physical bar-space specifics for BYOB — genuinely new information each time). **When Food and Bar share the same pill value and nothing else needs saying, show one plain pill row under the section heading (or, if a short qualifier is genuinely needed, fold it into the section's existing subtitle) with no subheaders and no restated prose** — Marchetti's fixed shape.
  - **Before collapsing Food and Bar into one shared row, check whether a real fee elsewhere on the page is itself evidence of a pill difference you haven't rendered yet (LondonHouse's fix, 2026-08-27).** LondonHouse's `-v2` build collapsed Food/Bar into one row because both looked like plain `All-Inclusive` — but Bar's own corkage fee (already sitting in `addOns`) only makes sense as a fee for something the venue would otherwise not serve, which is itself proof of a real BYO exception for wine/liquor. A fee tied to "bringing your own X" is a standing signal to re-check that side's pill set before treating Food and Bar as identical. This is the same class of gap as the "rendering is its own checklist item" rule above, one level deeper: here the *pill choice itself* needs a second look, not just whether a pill renders.
  - **Once you've confirmed a real difference exists, weigh how much structure it actually earns — a minor caveat doesn't need a full subsection split (LondonHouse's fix, same session, 2026-08-27).** The first attempt at fixing the Bar/corkage gap split Food and Bar back into full labeled subsections with a dedicated `BYO (Bring Your Own)` pill for Bar — reverted the same day on direct feedback ("i dont like this... think we can revert") as more structure than a one-line caveat needed. Landed shape: keep the single shared pill row (`All-Inclusive`, `In-house`), and add the caveat as a small caption underneath at the same weight as an existing plain-fact caption on the page (LondonHouse's `horsDoeuvresNote`, `text-xs text-gray-400`) — not a full `text-sm` prose paragraph, and not a second pill. Match the structure to how significant the nuance actually is: a genuinely different policy (BYO catering vs. exclusive-in-house) earns the full subsection treatment; a narrow fee-gated exception to an otherwise-identical policy earns a caption.

## 5. Authoring standard (non-negotiable, all venues already follow this)

- Every fact traces to a real, directly-fetched source page or PDF — no inferred/guessed numbers, ever. If the venue itself doesn't state something, the row says so (see Policies).
- Record real user feedback as dated inline comments in `data.ts`/`page.tsx` at the point of the change (`// feedback 2026-08-16: "..."` style, verbatim quotes when possible). This has been the practice all along and is genuinely useful — it's why this template doc could be written accurately from the existing venues instead of needing to interview anyone. Keep doing it.
- File header comment on `data.ts` states: why this venue was picked for the golden set, what's structurally different from prior venues, and what couldn't be sourced (with the specific reason — bot-walled Vimeo, Access-Denied JSON, etc.) rather than silently omitting.
- **A fact that legitimately needs restating in more than one section gets one shared constant, not independently-worded copies (LondonHouse's fix, 2026-08-27).** LondonHouse's corkage-fee/BYO nuance needed stating in Policies (the Bar row's detail), standardFaqs ("Can we bring our own alcohol?"), and the F&B section's caption — v2's first pass wrote it three separate times, and the three versions drifted enough that one row said "In-house only" while a nearby detail line described the exact opposite (a real BYO exception). Fix: define the sentence once (`const CORKAGE_NOTE = "..."` above the exported object, since a field can't reference its own object's other fields during construction) and reuse the same constant everywhere the fact appears, so a future edit to the fact can't silently leave one copy stale.
- `lastVerified` date + full `sourcePages` list always present.
- **Voice (2026-08-25/26, Greenhouse Loft): write plainly, in complete sentences, in Dewwey's own descriptive voice — not the venue's, and not visibly AI-generated.** Two specific tells to avoid, found and fixed across every user-facing string on this venue's page:
  - **No em dashes in authored prose.** They read as an AI tell, not a style choice ("you are writing too ai-y and there's so many em dashes... I'd rather use complete sentences and sound human"). Rewrite as two sentences, or use a comma/"and"/"so" instead. The one exception: a real verbatim quote from the venue's own site that happens to contain an em dash — that's the venue's writing, not ours, so it stays as transcribed. **This is a rendered-copy rule, not a comments rule** — dense, em-dash-heavy header comments explaining the *why* behind a change are this codebase's own established documentation style (every golden-set venue's `data.ts` header uses them) and are not something this cleanup touches; only strings that actually render on the page are in scope.
  - **Avoid a colon used as a dramatic-pause/elaboration device mid-sentence — another AI tell alongside the em dash (2026-08-26, Marchetti's fix: "limit em dashes and weird colons that won't seem normal to people").** Constructions like `"...deadline, though: the brochure says..."` or `"X build on each other: each package's bar offers..."` read the same way an em dash does — a stylistic tic, not how a person naturally writes the same fact. Rewrite as two plain sentences, or a semicolon joining two genuinely parallel clauses. A colon that's plainly introducing a list or a single value (`"Includes:"`, a `Label: value` UI pairing) is fine — the rule is against colons standing in for "and here's the elaboration," not colons in general. Also avoid stacking a closing parenthesis directly against a colon (`"...(Aperol Spritz Bar, Limoncello Spritz Bar): $12/guest"`) — reorder so the price follows the label directly (`"Signature Moments: $12/guest (Aperol Spritz Bar, Limoncello Spritz Bar)"`), which also reads more naturally out loud.
  - **Cite the source document in the adjacent code comment, not in the rendered copy the couple reads (2026-08-26, Marchetti's fix — "don't say stuff like per wedding brochure... this is so much simpler with [a plain fact]").** `"...per the wedding brochure"` / `"the brochure confirms..."` tacked onto an otherwise plain fact is filler a couple doesn't need — state the fact directly (`"A minimum applies to every event; any shortfall is added to the final balance."`) and move the citation to that field's own `//` comment, where it's still genuinely useful for the next person re-verifying the fact. **Exception:** when the copy's entire point is that two of the venue's own documents disagree (Marchetti's Payment schedule row), naming both documents is load-bearing content, not decoration — keep it there.
  - **Don't frame facts as "in their own words" / attributed quotes as a device.** State the fact directly in normal prose ("The venue offers an open catering list, so you can bring the caterer of your choice, as long as they're licensed and insured") rather than wrapping it in quotation marks and a "the venue says" preamble. The point of the page is to showcase the venue's real facts, not to perform having read their FAQ. A short, genuinely distinctive real phrase is still fine to quote occasionally (e.g. a policy's exact legal wording) — the rule is against making quote-attribution the default shape of every sentence, not against quoting ever.
  - **Say the venue's real name in body prose, not "the venue" (2026-08-26, Greenhouse Loft's fix).** "The venue offers an open catering list..." reads generic; "Greenhouse Loft offers an open catering list..." reads like it's actually about this venue. Use the real name to open a paragraph/fact, then "it" is fine for a second reference in the same sentence or the next one — the rule is against defaulting to "the venue" as the subject everywhere, not against the pronoun ever. Applies to Food & Beverage, Policies details, and standardFaqs answers alike.
  - **A venue's own internal/legal name (an LLC name, a "GHL"-style acronym from a contract) is real, but don't put it in visible copy unless the page has already introduced it to the reader.** Greenhouse Loft's real contract is titled "GHL Events, LLC Venue and Event Services Agreement" — genuinely their own shorthand, not invented — but nothing else on the page ever tells a couple what "GHL" means, so it reads as unexplained jargon if it shows up in a What's Included line. Use the venue's normal public name in visible strings; keep the legal/internal name in code comments and citations only.
  - **Word a one-sided contractual right as a right, not as an optional perk, when the source document shows no opt-out.** Greenhouse Loft's real contract grants the venue permission to assign its own videographer and use the footage for its own marketing — there's no checkbox for this and no couple-side opt-out anywhere in the document (contrast with the same contract's actual opt-in checklist for DJ/photobooth/security/etc.). First-pass copy said "GHL may film your event," which reads like something that might or might not happen at random; changed to "Greenhouse Loft reserves the right to film your event" — accurate to what's actually being agreed to. Check for a checkbox or explicit opt-out before wording anything as optional.
  - **No inline legal citations in visible copy** ("...(contract §2.3.1(C))"). It reads as clunky/bureaucratic, undercuts the "sound human" bar the em-dash rule above is already enforcing, and a couple has no use for a section number. Keep the citation in the adjacent code comment (where it's genuinely useful for the next person re-verifying the fact), not in the string a couple reads.
  - **Naming a specific real individual (an owner, a founder) in body copy is usually superfluous — the substantive fact carries the point without the name (2026-08-26, Marchetti's fix: "no need to name drop... that's superfluous").** "Family-owned and operated since [year]" already says what matters for a couple deciding on a venue; adding "led by [First] and [First] [Last]" doesn't add decision-relevant information, just specificity for its own sake. Keep names out of rendered copy unless the page has an independent reason to reference that specific person again (e.g. a named coordinator the couple will actually work with).
  - **Two similar "since [year]" facts about different entities are not the same fact — verify which entity each date actually describes before merging them into one sentence (2026-08-26, Marchetti's fix).** Marchetti's own `/about-us` page dates the *family's* restaurant lineage to 1924 (an earlier restaurant, Como Inn); its wedding brochure separately stamps *this specific venue* "EST. 1978." A first draft blurred these into one sentence that read as if the venue itself opened in 1924. Fix: state each date against the entity it actually describes, in separate sentences if needed, rather than the more dramatic-sounding but inaccurate single earliest date.
- **Real source documents that are dated/stale relative to the live site are still worth reading — extract structure, not stale numbers.** Greenhouse Loft's real service agreement was a January 2021 contract template with every dollar figure and percentage left blank (negotiated per booking) — clearly older than the live site's "2026-2027" pricing. Rather than discard it, it was used for the real *structural* facts it still reliably shows (a tiered cancellation schedule exists, a cleaning fee exists, overstaying is billed hourly, a real videography clause exists) without presenting any of its blank/negotiated numbers as public facts. Flag the document's dating explicitly in the file header comment, same as any other sourcing caveat — don't silently treat an old document as current, and don't silently discard it either.
  - **"Blank in the template" is a claim to verify, not assume — re-read the actual rendered pages before writing it down.** A fillable contract has two genuinely different kinds of fields: things that are blank because they're negotiated per booking (a dollar amount on a signature line, a date), and things that are printed, fixed terms the venue set once (a percentage table, a stated flat fee). Greenhouse Loft's first read of its own service agreement logged the cancellation-fee tiers and the cleaning fee as both "blank, negotiated per booking" — a second, closer read (2026-08-26) found both were actually printed in the document (a 25%/50%/100% table by days-out, a flat $500 cleaning fee) and had just been misread as blanks the first time through. If a document is worth citing as a source for "this exists but the number is blank," that claim needs the same direct verification as any other fact on the page — don't let a first-pass skim's characterization stand without literally checking it.
  - **A linked contract's own opt-in checklist can contradict the marketing site's "included" claims — flag it, don't silently pick a side.** Greenhouse Loft's marketing site (and its FAQ) states DJ/photobooth/security/parking/etc. are simply included in the flat rental fee. Its own real contract template has a literal checkbox list on its cover page: "INCLUDED IN TOTAL EVENT FEE (Included only if checked, all others are additional cost)" — the same items, gated. This may just mean the template is reused for non-wedding bookings where fewer boxes get checked, or it may mean the marketing site overstates what's automatically bundled; there's no way to tell without asking the venue. Note the tension explicitly in the file header comment when it comes up (What's Included is still built from the marketing site, the stronger/more couple-relevant source) rather than quietly trusting one document over the other.
- **Reading an image-based PDF with no text layer (no OCR, no ToUnicode CMap) needs page-image rendering, not `WebFetch`.** `WebFetch` converts HTML to markdown and chokes on a raw scanned/flattened PDF — it'll report back that the content is "a raw PDF binary stream, not human-readable," even though the file is a real, readable document once rendered. This has come up repeatedly (Diamond Garden's menu PDFs, Greenhouse Loft's catering-guidelines and service-agreement PDFs). The reliable path: render each page to a PNG (`pdftoppm -png -r 150 file.pdf out-prefix`, via `poppler-utils`) and read the images directly with the multimodal `Read` tool. If `poppler-utils` isn't installed and there's no root, it can still be obtained without sudo: `apt-get download poppler-utils` (and its runtime deps as `ldd` reports them missing — typically `libpoppler<N>`, `libopenjp2-7`, `libnss3`, `libnspr4`, plus whatever `ldd` flags next) into a scratch dir, `dpkg-deb -x <pkg>.deb ./extract` each one (no install, just unpacks the files), then run `pdftoppm` with `LD_LIBRARY_PATH` pointed at the extracted `.so` directories. Same trick works for getting a headless Chromium running (via `playwright-chromium`) to screenshot a page for a design review when nothing's installed system-wide.
